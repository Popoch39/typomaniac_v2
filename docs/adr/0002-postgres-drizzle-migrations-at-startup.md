# Database: PostgreSQL (Bun.SQL) + stable Drizzle, migrations applied at API startup

The API persists its data in PostgreSQL, through Drizzle ORM `0.45` (latest stable version) and the `Bun.SQL` driver (`drizzle-orm/bun-sql`). Migrations are generated by `drizzle-kit generate`, versioned in `apps/api/drizzle/`, then applied by the server itself at startup, before `listen()`, under a `pg_advisory_lock`. The prod image is a compiled Bun binary on a distroless base, without drizzle-kit: that is why migration is built into the app. Postgres runs in a container: `compose.yaml` (Postgres only) in dev and for tests, `compose.prod.yaml` (Postgres + API) in prod.

## Considered Options

- **SQLite (`bun:sqlite`)**: it was the first choice, abandoned before any commit. We want a real database server that accepts several API processes and offers Postgres features. One more service in the compose is an accepted cost.
- **Drizzle `1.0.0-rc`**: rejected in favor of the stable version. The RC provides `drizzle-orm/typebox`, which generates TypeBox 1.x schemas compatible with Elysia 2. Without it, HTTP schemas are written by hand.
- **`drizzle-typebox` with Drizzle 0.45**: rejected. It depends on `@sinclair/typebox` 0.x, incompatible with Elysia 2's `typebox` 1.x.
- **`postgres` (postgres.js) or `pg` driver**: rejected. `Bun.SQL` is built into the runtime, adds no dependency and compiles into the binary.
- **Tests on PGlite or testcontainers**: rejected. PGlite is not the prod engine, and testcontainers adds a dependency and a slow startup. Tests use the dev compose's Postgres.
- **Migrations in a separate service** (job or dedicated container): rejected. It would need a second image with drizzle-kit. The advisory lock is enough to serialize several replicas.

## Consequences

- `DATABASE_URL` is required to run the API, the tests and drizzle-kit.
- `bun test` requires a running Postgres (`docker compose up -d`). Each test file creates its own migrated database, then drops it.
- Drizzle 0.45's migrator refuses to start without `meta/_journal.json`. An empty initial migration (`0000_init.sql`) therefore serves as the starting point.
- Moving to Drizzle 1.0 one day means reworking the migrations folder format and replacing the hand-written TypeBox schemas with `drizzle-orm/typebox`.
- The `apps/api/drizzle/` folder is copied into the runtime image. The server reads it from its working directory (`MIGRATIONS_DIR`, default `./drizzle`).
- Prod data lives in the `postgres-data` named volume of `compose.prod.yaml`. The backup strategy (scheduled `pg_dump`, etc.) remains to be decided.
